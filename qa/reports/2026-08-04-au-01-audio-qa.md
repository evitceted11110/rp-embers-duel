# 《餘燼決鬥場》AU-01 音訊唯讀驗收

日期：2026-08-04  
範圍：雙職業 24 張卡、8 條共鳴，以及現有 Web Audio 啟動／混音／靜音契約。  
方式：唯讀程式與事件表稽核、既有自動測試、local Vite 啟動檢查；未修改 runtime、未 commit／push／deploy。

## 結論

**不放行 Gate 3 前的 AU-01。** 傳統 1.0 音訊的首次互動、三匯流排、總靜音、危險預兆和既有操作 cue 均有自動證據；但雙職業的 24 張卡成功事件與 8 條共鳴尚未取得可辨識的事件映射。它們目前被壓縮為兩種通用聲音，無法讓玩家以聲音辨別自己觸發了哪種職業行為或共鳴。

## 阻斷 Gate 3 前工程

### AU-01-1：24 張職業卡成功事件沒有逐卡可辨識音訊映射

- **依據：** Audio Director 完成判準要求玩家操作、危險、成功與失敗具可盲測區分；本工作包要求 24 張 typed success events 正確映射。
- **現況：** `src/audio/audio-frame.ts` 的 `eventCue()` 對 `classEffectResolved` 只有一個 card 特例：`pressure-furnace-roar` 回傳 `player-blocked`；其餘 **23 張卡**全回傳 `skill-e`。`content/audio-events.json` 沒有任何雙職業 card ID cue。
- **重現：**
  1. 執行 `rg -n "classEffectResolved|resonanceResolved" src/audio/audio-frame.ts content/audio-events.json`。
  2. 對照 `src/core/types.ts` 的 24 個 `classEffectResolved` union 成員與 `src/core/class-expansion.ts` 的 24 張 `CLASS_CARDS`。
  3. 可見不同的主手、Q、E 成功行為（例如雙釘封口、環扣索、回爐移釘）皆落到同一 `skill-e` cue，沒有 cardId 分流。
- **精準修正項：** 在結構化 cue 表新增 24 張 card-success cue（或保留少量共享的、經音色＋節奏證明可盲測區分的行為族群），並以 `classId + cardId + effect` 的封閉 map 取代目前 fallback。每項 cue 應至少在 waveform／節奏／頻率輪廓其中兩項與同槽近似效果不同；補一個測試遍歷全部 typed `classEffectResolved`，斷言 map 完整且其 cue ID 存於 events 表。

### AU-01-2：8 條共鳴與其拒絕原因沒有逐條音訊因果

- **依據：** Audio Director 完成判準的成功／失敗可辨識性；Gate 2 規格的共鳴可讀因果；本工作包要求 8 條共鳴正確映射。
- **現況：** `eventCue()` 對 `resonanceResolved` 僅以職業二分：四條熔衛共鳴全是 `player-blocked`，四條影線共鳴全是 `skill-e`。八條 `resonanceRejected` 全為同一 `skill-failed`；`classCardSelected` 和 `resonanceAvailable` 亦共用 `draft-offered`。音訊表中沒有共鳴名稱或拒絕 reason。
- **重現：**
  1. 在 `src/core/class-expansion.ts` 列出 `防區反震`、`封口回收`、`楔點轉掃`、`錨索退讓`、`線路收割`、`折返處刑`、`吊點脫身`、`交線換身`。
  2. 對照 `src/audio/audio-frame.ts` 的 `resonanceResolved`／`resonanceRejected` 分支。
  3. 觸發任一同職業共鳴時均獲得同一 cue，無法從聽覺辨別前置物、成功結果或錯誤幾何。
- **精準修正項：** 在 events JSON 建立 8 個 resolve cue；將 `resonanceRejected` 至少分成「缺少前置物」「錯誤幾何／落點」「時機／格擋失敗」三種節奏／音色不同的拒絕 cue，HUD 仍保留現有文字 reason。補測試遍歷 `RESONANCE_VISUAL_CUES` 和所有 `resonanceRejected` union，驗證每個 resolved 名稱與 reason 都可解析到既有 cue，且 cue 有可區別的節奏或 waveform。

### AU-01-3：瀏覽器人耳／console 驗收尚無法取得

- **依據：** `design/audio-guide.md` 的真人瀏覽器驗收、Audio Director 的「首次互動後啟動」與 cue 延遲目標。
- **現況：** local Vite 已成功啟動於 `http://127.0.0.1:4173/`，但本工作環境沒有可連接的 Browser 執行個體，控制層回覆「No browser is available」。因此無法實測首次互動前後 `AudioContext`、音量 slider、mute、console error 或人耳混淆矩陣。
- **重現：** 啟動 `pnpm dev --host 127.0.0.1 --port 4173` 後，在具 Chrome/Chromium 的環境載入頁面；以 DevTools Console 與 AudioContext state 檢查第一次 pointerdown/keydown 前後，再測三個 slider、mute 和雙職業流程。
- **精準修正項：** 這是驗收環境缺口，非 runtime 改碼要求。待 PF-01 的 Chromium 環境可用後，以同一 1280×720 trace 補交互 smoke、console 0 error、依音色／節奏的盲聽混淆矩陣；在 AU-01-1、AU-01-2 修正後才有足夠不同 cue 可做盲測。

## 放行條件

AU-01 僅可在以下四項都完成後放行：

1. 24 張 `classEffectResolved` 逐卡／經驗證行為族群的閉合映射與自動測試。
2. 8 條 `resonanceResolved` 與所有 typed rejected reason 的可辨識映射與自動測試。
3. `pnpm verify` 維持全綠。
4. Chromium 實測：首次互動前無 autoplay、互動後 audio running、三 bus／mute 正常、靜音全流程可完成、console 0 error，並完成 cue 混淆矩陣。

在上述完成前，**不放行 Gate 3，也不宣稱雙職業音訊已驗收。**
