## 0. 這份文件要解決什麼

Gate 2 已放行進入 Vertical Slice。使用者裁示兩件事：(1) 工作室不設固定視覺識別，本款依內容個別決定；(2) 本款要「勇者地下城 像素的那種風格」。

本文件提出 **3 個彼此在解析度、實作路徑、判定可讀性解法上都真的不同**的方向，不是同一個點子換色。每個方向都要正面回答一個結構性難題：**《餘燼決鬥場》的核心設計主張是十二枚印記直接改寫動作的幾何形狀**（弧線、120° 扇形、殘影、0.15 秒格擋尾段），而像素風格的低解析度網格天生會犧牲精確幾何的可讀性——這兩件事有真實張力，不能迴避。

## 1. 「勇者地下城」查證：使用者的參照是什麼

搜尋沒有找到一款明確叫《勇者地下城》的作品。最可能的指涉脈絡是 **Pixel Dungeon**（Watabou）與其各種 remix/衍生——「勇者＋地下城＋像素」在中文語境最常見的對應。查證到的具體事實（僅列可查證者，不擴充）：

- Pixel Dungeen 為**回合制**傳統 roguelike，圖像採 **16×16 像素**磚塊，介面精簡；素材以 GPLv3 釋出。（來源：[watabou/pixel-dungeon GitHub](https://github.com/watabou/pixel-dungeon/blob/master/README.md)、[OpenGameArt 素材頁](https://opengameart.org/content/pixel-dungeon-graphics-by-watabou)）

**這裡有一個必須點出的落差**：Pixel Dungeon 是回合制——它的「精確判定」問題不存在，因為沒有連續時間下的弧線位移、沒有 0.15 秒格擋尾段這種即時窗口，格子與行動都是離散的。《餘燼決鬥場》是**即時動作**遊戲。如果使用者腦中的畫面真的是 Pixel Dungeon 那種 16×16 磚塊回合制觀感，直接套用在本作會遇到真正的結構問題，而不只是美術調性問題。

因此本文件額外查證了**即時動作類像素遊戲**如何解決「低解析度＋精確判定要可讀」這個問題，作為更貼近本案真實需求的技術參照（僅陳述查證到的具體事實）：

- **Enter the Gungeon**：內部原生解析度 480×270，美術像素與螢幕像素採整數倍映射（1080p 下 1 顆美術像素＝4×4 螢幕像素），刻意不對像素做旋轉/縮放形變，避免像素抖動與「像素蠕動」。（來源：[Steam 社群討論](https://steamcommunity.com/app/311690/discussions/0/364039785159426921)）
- **Nuclear Throne**：原生解析度 320×240，一律用最近鄰（nearest-neighbor）整數倍放大，不用非整數縮放，避免鋸齒不均。（來源：[Steam 社群討論](https://steamcommunity.com/app/242680/discussions/0/490125103621697726/)）

這兩款都是「即時、需要精確彈道/攻擊判定可讀」的像素動作遊戲，比 Pixel Dungeon 本身更貼近《餘燼決鬥場》要解決的問題，因此下方三個方向都以「整數倍縮放的低內部解析度」為共通技術基礎，但在**判定形狀怎麼處理**這件事上分岔成三種不同哲學。

**如果使用者的參照其實就是字面上的 Pixel Dungeon 回合制觀感**——那本文件的判斷是：那個觀感與本作「即時三段連擊＋弧線閃避＋0.15 秒格擋窗」的核心設計主張有結構性衝突，不是美術問題，這件事應該由人類確認後才進入 Vertical Slice，而不是美術硬把回合制美學塞進即時戰鬥。三個提案因此都不是「精確複刻 Pixel Dungeon」，而是「像素動作遊戲」譜系下的不同取捨，若這偏離了使用者的想像，請現在指正。

## 2. 共通問題一：判定形狀 vs 像素網格的張力，三個方向各自怎麼解

三個方向對這個張力給出**不同的答案**，不是同一個解法的變體：

| 方向 | 解法哲學 |
|---|---|
| 提案一 | 分層：世界用粗像素，判定形狀用不服從像素網格的乾淨疊層——刻意打破「全畫面都是像素」的純粹性，換取判定永遠清楚 |
| 提案二 | 不分層：判定形狀也活在同一張像素網格上，鋸齒本身就是本作的視覺身份——用足夠的解析度密度讓鋸齒仍然可讀，不用作弊層 |
| 提案三 | 角色與判定形狀分屬不同資產性質：角色是像素精靈圖，判定/特效層是完全自由的發光向量——用實際素材換取角色個性，同時讓判定層不被像素綁死 |

## 3. 共通問題二：色彩語意衝突（三流派色 vs 敵人預兆色）

`content/enemies.json` 與 Boss 已固定敵人預兆色的語意：**紅圈＝範圍重擊、藍線＝突進衝撞、綠符文＝召喚**（焰奴的紅色蓄力光暈也屬此系）；甲衛用白色扇形預警。`content/marks.json` 的 `visible_feedback` 欄位也已隱含三流派的色相家族：裂焰＝暗紅→橘（核心武裝色）、影步＝藍紫（殘影）、守勢＝灰藍（護環）＋金（滿層描邊）。

**衝突點**：裂焰的橘紅系與敵人「紅圈重擊」共用紅色系警戒色域；守勢的灰藍與敵人「藍線衝撞」共用藍色系。混戰中玩家可能把自己的印記特效誤認成敵方預兆，或反過來。

三個提案共同採用的緩解策略（雙軸編碼，非本文獨創手法，是即時動作遊戲常見慣例，不掛名特定作品）：

1. **色相位移**：玩家／流派色一律**偏離敵人預兆的純色**——裂焰用飽和的琥珀橙而非純紅，守勢用偏青的鋼藍而非純藍，避免直接撞色。
2. **形狀與錨點雙重區隔**：敵人預兆固定是「投影在地面的硬邊幾何」（圓圈、直線、扇形，見 `telegraph_tell`），玩家／流派特效固定是「附著在角色本體或武器上的效果」（護環、殘影、核心圖示）。即使色相偶爾相近，「地面 vs 角色」「硬邊 vs 柔邊/粒子」這兩條額外訊號足以避免誤讀。

下方三個提案的色彩系統都遵守這兩條規則，敵人色固定沿用同一組（不因方向而變，因為那是已定案的遊戲語意，不是美術可自由發揮的部分）：

**敵人預兆色（三案共用，不列入各案的 4–6 色配額）**
| 色 | Hex | 語意 |
|---|---|---|
| 警戒紅 | `#e6283c` | 焰奴蓄力光暈／Boss 紅圈重擊 |
| 衝撞藍 | `#2e6fe6` | Boss 藍線突進衝撞 |
| 召喚綠 | `#3ecb6b` | Boss 綠符文召喚 |
| 甲衛白 | `#f2efe6` | 甲衛地面扇形預警 |
| 影刺客暗色 | `#1a1620` | 下蹲蓄勢殘影軌跡（`enemies.json` 僅描述「暗色」，未定 hex，此處給出可用值） |

## 提案一：巨像素微縮舞台（Macro-Pixel Diorama）

### 一句話定位

戰場是一座用粗大方塊像素堆出來的微縮沙盤，判定形狀是浮貼在沙盤上方、不服從像素網格的乾淨描邊光層——世界很像素，規則不將就。

### 色彩系統

背景走「黑曜決鬥場」的暗黑基調（呼應 spec 的場景命名）。

| 職責 | Hex | 說明 |
|---|---|---|
| 背景／黑曜岩底色 | `#14110f` | 近黑暖炭色，整體場景基底 |
| 環境中性色 | `#3a3229` | 地磚、牆體的暗石色，與背景拉開一階明度即可，避免死黑一片 |
| 裂焰流派色 | `#ff8c3c` | 核心武裝、扇形連擊——琥珀橙，刻意偏離敵人警戒紅 |
| 影步流派色 | `#7c5cff` | 殘影、E 瞬移特效——藍紫 |
| 守勢流派色 | `#5c8fae` | 護環基色——鋼青藍，滿層時描邊轉 `#e8c14d`（金） |

### 解析度與縮放策略

- 內部渲染解析度 **160×90**，整數放大 **8 倍**至 1280×720（`1280/160=8`、`720/90=8`，兩軸放大倍率相同，避免非等比縮放造成的像素變形）。
- 世界層（角色、地形、敵人本體）鎖在這張 160×90 網格上，每個「巨像素」在螢幕上是 8×8 實體像素的色塊，走 Nuclear Throne／Enter the Gungeon 驗證過的最近鄰整數縮放，不做旋轉與非整數縮放。
- **判定/回饋層獨立於世界層之上**，以更高的內部細分（例如 640×360，或直接用原生 1280×720 畫布疊加）繪製，只包含：閃避弧線軌跡、扇形判定範圍、殘影本體、格擋尾段光環。這層允許反鋸齒、允許次像素移動——這是本方向刻意打破「純像素」的地方。
- 不允許次像素移動的只有世界層（避免巨像素抖動）；判定層允許，因為 0.15 秒的格擋尾段禁不起被 8px 網格量化成「看得到但慢半拍」。

### 形狀語彙

- **弧線（餘燼核心閃避路徑）**：世界層角色仍是巨像素移動（每幀落在 160×90 網格上），但移動路徑本身由判定層畫出一條平滑的橘色曲線殘跡（寬 2px、發光），讓玩家看得出「這一次閃避是彎的」，即使身體本身移動時仍是巨像素跳格。
- **120° 扇形（裂焰連擊）**：判定層畫出一個乾淨的扇形色塊＋描邊（非鋸齒），世界層同時在對應巨像素上疊一層橘色調色（tint），讓扇形範圍「看起來也燒到了地面」，但精確角度由判定層負責，不會因為世界層網格太粗而讓 120° 誤判成 90° 或 150°。
- **殘影（精準殘影／影步）**：判定層直接複製角色輪廓、降低不透明度、加柔邊模糊，比世界層的角色本體更平滑——「幽靈比肉身更滑」是刻意的視覺語言，暗示殘影是「規則」不是「物質」。
- **格擋尾段（蓄能反震 0.15 秒）**：角色巨像素輪廓外圍，判定層疊一圈細光環，尾段觸發時光環瞬間增亮＋外擴一圈再收回（3–4 幀動畫，0.15 秒在 60fps 下約 9 幀，足夠做出「亮起→撐開→收回」三段式的清楚閃現）。

### 實作路徑

**(A) 全程式化**，且是本三案中對「程式化」最徹底的一案：世界層與判定層都是 canvas 繪圖指令產生（矩形、圓弧、路徑），沒有任何點陣圖檔案。角色造型用少量色塊拼出剪影（軀幹矩形＋武器線條＋2–3 個強調色像素代表眼睛/核心），敵人三種靠輪廓比例與顏色區分（焰奴矮胖、影刺客瘦長、甲衛方正厚重）。視覺隨機（例如受擊時的巨像素碎裂粒子方向）一律走 `rng.fork('visual-diorama')`。
代價：角色個性完全靠形狀比例與顏色傳達，沒有五官/表情，第一印象的「可愛度」或「威嚇感」會比手繪素材弱；雙層渲染（世界層+判定層）需要兩套 canvas 或兩個 draw pass，架構比單層複雜，但仍在純 Canvas API 範圍內，不需要額外套件。

### 最適合 / 最不適合

- **最適合**：想要濃厚「復古地下城探索」氛圍、同時堅持判定必須零妥協地精準可讀的方向；零素材授權風險、迭代最快，最貼合工作室「初期程式化為主」的既定策略。
- **最不適合**：如果使用者想要的是「連特效都不能跳出像素顆粒感」的硬派像素原教旨主義——這個方向的判定層刻意不是像素的，會被這類玩家認為「不夠純」。

### 構圖示意：餘燼核心引爆瞬間

```
┌──────────────────────────────────────────┐
│ 黑曜岩地面（8x8 巨像素鋪滿）               │
│                                            │
│        ◇ 核心(橘,已武裝,脈動外環)          │
│       ╱                                    │
│      ╱  ← 判定層：平滑橘色弧線殘跡（閃避路徑向核心彎曲）

│                                            │
```

## 提案二：中解析度戰術像素（Tactical Pixel, 鋸齒即身份）

### 一句話定位

判定形狀就活在像素網格裡，鋸齒不是妥協而是本作的視覺身份——用足夠高的內部解析度密度，讓弧線、扇形、殘影在鋸齒狀態下仍然一眼可讀，不靠額外的「乾淨疊層」作弊。

### 色彩系統

比提案一更高飽和、更高對比，貼近經典 indie 像素動作遊戲（Nuclear Throne／Enter the Gungeon 一類）的「畫面很吵但看得懂」調性。

| 職責 | Hex | 說明 |
|---|---|---|
| 背景底色 | `#0c0e12` | 更冷的近黑，對比後續高飽和強調色 |
| 環境中性色 | `#2b2f3a` | 冷灰藍調地磚/牆體 |
| 裂焰流派色 | `#ff6a1a` | 更飽和的橘，判定層在小尺寸下仍需要靠高飽和撐住可讀性 |
| 影步流派色 | `#9b4dff` | 更飽和紫 |
| 守勢流派色 | `#4fb3d9` | 更飽和青藍，滿層描邊 `#ffd54a` |

### 解析度與縮放策略

- 內部渲染解析度 **320×180**，整數放大 **4 倍**至 1280×720。這個密度刻意對齊 Enter the Gungeon 的等效密度（其 480×270 內部解析度對應 1080p 輸出；1080p→720p 的等比縮放係數為 720/1080=0.667，480×0.667≈320，270×0.667=180——即本案 320×180 在 720p 下與 Gungeon 在 1080p 下的「每畫面像素密度」相當）。
- 全畫面單一像素網格，**沒有分層例外**：世界、角色、判定形狀、特效全部畫在同一張 320×180 canvas 上，一次最近鄰整數放大輸出。
- 不允許次像素移動——所有位置在渲染前都先量化到整數格點，讓移動本身也有清楚的「一步一步」踏格感，這是本方向刻意的機械感語彙，呼應「印記改寫規則」的主張（規則感=格點感）。

### 形狀語彙

- **弧線（餘燼核心閃避路徑）**：用程式化的圓弧點陣演算法（依角度逐格取樣）畫出階梯狀弧線軌跡，寬度 2–3 格，搭配比周圍地板亮兩階的顏色，讓「這是一條弧線」在鋸齒狀態下仍能被形狀輪廓辨認，而非追求平滑曲線的錯覺。
- **120° 扇形（裂焰連擊）**：填色扇形直接在網格上點陣化，邊緣鋸齒但用一圈比填色更亮一階的邊界像素描邊，讓扇形的兩條邊界線在戰鬥雜訊中仍能被抓出來。320 格寬的內部解析度下，一個半徑 2.2 units 的扇形大約能佔到 25–35 格寬，足夠讓 120° 角度的「開口感」被辨認（對照提案一 160×90 下同樣範圍只佔約 12–17 格，開口角度容易被誤讀成鈍角或直角）。
- **殘影（精準殘影／影步）**：殘影＝角色剪影的完整複製幀＋固定的透明度階梯（例如 60%→30%→0%，只用 2–3 個離散透明度值而非連續漸層，維持像素風格的「一階一階」質感），色相偏移至流派色而非單純變透明，讓殘影在忙碌畫面中仍有色彩辨識度。
- **格擋尾段（0.15 秒）**：角色輪廓外緣整圈同色高亮 1 格寬，觸發瞬間切換為對比色（例如守勢青藍→白）並維持 2 幀，是本方向對「短暫時間窗口」的解法——不靠平滑動畫，靠**顏色瞬間切換**在像素風格下反而更銳利、更符合「格點感」的機械語彙。

### 實作路徑

**(A) 全程式化**，比提案一更依賴「像素級演算法」本身（點陣化圓弧/扇形/量化透明度階梯），實作複雜度略高於提案一（提案一可以偷懶用平滑向量畫判定層；本案每個形狀都要手刻點陣化邏輯），但仍是零外部資產、零授權疑慮。視覺隨機一樣走 `rng.fork()`。
代價：小尺寸判定形狀（例如格擋尾段的 1 格寬高亮圈）在畫面雜訊多時可能被其他效果的像素蓋掉，沒有提案一那種「保底疊層」可以救援，必須靠色彩對比與閃爍頻率彌補，容錯空間比提案一小；點陣化演算法需要更多手調（例如圓弧在不同半徑下的鋸齒觀感需逐一測試），前期打磨時間比提案一長。

### 最適合 / 最不適合

- **最適合**：想要「這就是純粹的像素動作遊戲，連判定形狀的鋸齒感都是設計語言一部分」的方向，畫面調性最貼近經典 indie 像素 roguelite 的硬派質感。

## 提案三：剪影＋墨光（Silhouette + Ink Glow，混合資產路線）

### 一句話定位

角色是有臉、有個性的小型像素精靈圖，但所有判定幾何（弧線、扇形、殘影、格擋尾段）完全跳脫像素網格，以自由發光的墨光層表現——用實際素材換取角色辨識度與行銷截圖的表現力，用不受像素綁死的特效層解決精確判定的可讀性。

### 色彩系統

比前兩案更偏「寶石色」的濃郁調性，因為發光墨光層可以在深色精靈圖上做出更豐富的明暗層次。

| 職責 | Hex | 說明 |
|---|---|---|
| 背景底色 | `#171018` | 深梅黑，比前兩案更暖／更深 |
| 環境中性色 | `#46392f` | 暖石棕，讓精靈圖輪廓在環境中站得出來 |
| 裂焰精靈圖基色 | `#b5502e` | 角色/敵人素材本身的暗赭色（低飽和，作為素材基底） |
| 裂焰墨光色 | `#ffab52` | 核心、扇形等判定層專用高飽和暖光 |
| 影步精靈圖基色／墨光色 | `#4b3f73` ／ `#a48cff` | 素材基底偏悶紫；判定層墨光偏亮藍紫 |
| 守勢精靈圖基色／墨光色 | `#3f5a63` ／ `#7fd0e8`（滿層 `#f0cf6b`） | 素材基底偏悶青；判定層墨光偏亮青 |

### 解析度與縮放策略

- 世界／地形內部解析度 **256×144**，整數放大 **5 倍**至 1280×720。
- **角色與敵人是實際精靈圖**（美術以小尺寸畫布繪製，例如每個角色 32×48 像素的畫布，再整數放大貼進 256×144 世界網格），走 nearest-neighbor 縮放維持邊緣銳利。三流派可用「單一角色基礎精靈圖＋色板替換（palette swap）」降低素材量——只需畫一套灰階/中性色的基礎幀，三種流派親和力用程式做調色板替換即可換色，不必畫三套完整動畫。
- **判定/特效層完全脫離像素網格**，直接畫在原生 1280×720（或更高）畫布上：弧線是平滑曲線光跡，扇形是柔邊漸層光墨，殘影是模糊發光的半透明色塊複製（非精靈圖複製，是純光影），格擋尾段是一圈脈動光環。這層允許次像素移動、允許反鋸齒、允許粒子系統。
- 這是三案中**唯一角色本體需要外部資產管線**的方向，判定層則走與提案一類似的「乾淨疊層」邏輯，但更進一步——提案一的判定層還算「像素風格的乾淨線條」，本案的判定層是完全不裝作像素的自由發光效果（更像現代 indie 遊戲在像素精靈圖上疊加光效粒子的常見做法，此處不掛名特定作品，因為未查證到可具體引用的單一案例，僅描述做法本身）。

### 形狀語彙

- **弧線**：判定層直接畫平滑貝茲曲線光跡，末端帶粒子拖散（用 `rng.fork('visual-trail')` 決定粒子的隨機抖動，維持決定性可重現）；角色精靈圖本身的移動幀仍是像素步進動畫，光跡飄在其後方或周圍，不需要精靈圖本身變形。
- **120° 扇形**：柔邊光墨扇形，中心亮、邊緣漸淡，角度邊界用一條清晰的高光細線標出（因為漸層本身邊界會模糊，需要這條線來鎖定精確角度，避免玩家誤判扇形範圍）。
- **殘影**：不是精靈圖的半透明複製（那樣會顯得廉價），而是精靈圖剪影投影＋色彩光暈的組合——保留輪廓可辨識（玩家看得出「那是我」），但整體發光模糊，質感介於「殘留的燃燒印記」與「幽魂」之間。
- **格擋尾段**：角色精靈圖外緣的自由發光光環，脈動一次（放大→收縮），因為不受像素網格限制，這個 0.15 秒動畫可以做出更細膩的漸強漸弱曲線，是三案中格擋尾段觀感最平滑的一版。

### 實作路徑

**(B) 精靈圖／混合**，是三案中唯一偏離「全程式化」策略的方向：
- 角色與敵人本體＝實際美術資產（手繪或 AI 生成，需另外決定來源與授權——工作室尚未有美術資產管線，這是本方向要付的架構代價）。
- 判定/特效層仍可以完全程式化（canvas 繪圖＋粒子系統，視覺隨機一樣走 `@rogue-paradise/rng` fork stream）。
代價：
1. 引入資產管線本身（無論手繪或 AI 生成，都需要之後決定素材來源、授權確認、風格一致性把關——12 枚印記＋3 流派＋3 種敵人＋Boss 共需要相當數量的幀，且要求「像出自同一隻手」）。
2. `agents/visual/AGENT.md` 的完成判準明確要求「視覺元素全部由程式產生，沒有硬編碼的外部圖檔路徑」——本方向的角色部分不符合這條，若採用需要向 Studio Head 說明例外理由並取得認可，不是既有規範下的預設路徑。
3. Vertical Slice 的時程壓力下（Gate 3 試玩），額外的素材產出/取得時間可能拖慢節奏，且素材品質不穩定的風險（尤其若走 AI 生成）比純程式化更難預先保證。

### 最適合 / 最不適合

- **最適合**：如果使用者更在意角色/敵人有辨識度、有「臉」、行銷素材與截圖表現力強，且工作室願意承擔資產管線的前期建置成本（授權、風格把關流程）。判定形狀的可讀性壓力在三案中最小，因為特效層完全自由。
- **最不適合**：如果工作室現階段仍要維持「零資產授權風險、迭代最快」的既定策略（`agents/visual/AGENT.md` 明訂的完成判準），或 Vertical Slice 時程吃緊，這個方向引入的管線成本與規範例外都不成比例；也不建議在還沒驗證核心玩法好不好玩之前，就投入美術資產成本。

## 5. Visual Director 的建議（挑選權在人類）

三案在技術上都可行、都能通過「判定形狀必須讀得出來」這條硬要求，差別在於**代價落在哪裡**。

個人建議傾向**提案一（巨像素微縮舞台）**，理由：

1. 這是目前唯一在**判定可讀性**與**工作室既有的「程式化為主、零資產風險」策略**之間沒有明顯取捨的方向——提案二把可讀性的容錯空間讓給了「像素純粹性」，提案三把「零資產風險」讓給了角色表現力。
2. Vertical Slice 現階段的驗收目標是「核心循環好不好玩」（Gate 3），不是「畫面好不好看」；提案一能最快做出可驗證判定形狀清晰度的原型，且不需要額外的資產授權決策擋在前面。
3. 若 Gate 3 真人測試後發現使用者其實想要的是提案二那種「更硬派、更純像素」的顆粒質感，或提案三那種「有臉有個性」的角色表現力，屆時再依真人回饋加碼調整（例如把判定層的疊層做得更貼近像素質感，或後續補上精靈圖角色），比一開始就選了難以回頭的方向風險更低。

但**這只是建議，不是決定**——尤其若使用者對「勇者地下城」的想像其實更接近提案三那種「有個性的角色」，或使用者認為判定可讀性可以靠 Gate 3 微調解決、更在意提案二的硬派像素純粹感，都是合理的選擇，最終方向請人類拍板。

## 6. 尚待人類確認的一件事

若第 1 節提到的「Pixel Dungeon 是回合制，本作是即時動作」這個落差，代表使用者實際想像的視覺參照跟本作的核心玩法設計有結構性差異——這件事本身值得先確認過一次，而不是美術單方面用「像素動作遊戲」的譜系去詮釋「勇者地下城」四個字。若確認後方向不變，以上三案仍然成立；若使用者想要的其實是更貼近回合制/棋盤格的呈現，則需要回頭與 Designer／Gameplay Engineer 討論這是否影響核心循環本身，而不只是換一套美術。
