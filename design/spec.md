## Gate 3 核心戰鬥修訂（2026-08-03）

### 真人第四次回饋落地：劍光與玩家普攻碰撞 envelope

- 真人指出「實際劍光碰到敵人，但碰撞區明顯過小」。根因不是單一 range 數字：舊 core 只檢查敵人腳點／中心是否落在扇形內，忽略 sprite hurtbox；render 又在裂焰／追擊／鐵壁分支另寫 2.2、2.5、×1.3，且命中後追擊窗口會被消耗，造成 VFX 重算錯誤。
- 三段 base physical blade reach 校準為 **1.30／1.45／1.95 units**；在 640×360、22px/unit 下，中心線為 **28.6／31.9／42.9px**，加上 8／9／11px 主刃帶的半寬後，最外可見刃緣為 **32.6／36.4／48.4px**。半角為 61.2°／54°／75.6°。damage、HP、敵速與 content 數值不變。
- `PlayerAttackGeometry` 是 base 三段與裂焰連擊、突進追擊、鐵壁連動的唯一主斬幾何來源，包含 active 起點、facing、physical reach、half-angle、hit index、可見 stroke 半寬與 hurtbox 規則。startup／active cue、combat 與命中後 VFX 讀同一 helper／快照，不得在 render 另寫距離倍率。
- 敵人使用按 kind 固定的 deterministic 圓形 hurtbox：焰奴 0.50、影刺客 0.42、甲衛 0.72、Boss 1.00 units。命中定義為「目標 hurtbox 圓與主斬扇形／可見刃帶相交」，同時精確檢查徑向外緣與兩條角度側邊，不得退化為只做 `range + radius` 的中心距離判斷。
- physical blade reach 是劍光中心線的主動攻擊距離；hurtbox overlap 是允許可見刃帶擦到敵人身體時命中的接觸規則，不是把武器本身偷偷延長。裂焰的主斬仍是同一扇形；`secondary_splash_damage` 是命中主目標後才觸發的獨立圓形 splash，不得拿 splash 圓替代主斬 sector。
- `comboHit`／`comboWhiff` 與 active `ComboState` 都保存命中當刻 geometry；因此 pursuit window 清零、guard stack 改變或玩家已完成 lunge 後，startup／active cue 與殘留劍光仍不會改成另一個範圍。

### 真人第三次回饋落地：輕輕重、追逃、命中反應與場界

- 普攻是明確的**輕、輕、重**：第一／二段 startup 0.05s、active 0.04s，第三段 startup 0.11s、active 0.08s；這些動作時間與段間連接窗口分開計算。第一段 active 結束後有 **0.10s** 連接窗口，窗口內輸入會在窗口結束接第二段；第二段後為 **0.20s**，接第三段重擊；第三段後 loop 窗口定義為 **0.20s**，接回第一段。窗口逾時未輸入即回 idle，之後再按必須從第一段開始。held 視為持續的後續輸入意圖，故完整循環為 0.19／0.29／0.39s，合計 **0.87s**，並無限循環 1→2→3→1。傷害維持 8／10／16；physical reach 為 1.30／1.45／1.95 units。第三段半角 75.6°、推進 0.22 units、命中 recoil 0.32 units，均明顯高於輕擊。任一連接窗口仍可用閃避取消。
- 玩家正常移速為 **6.5 units/s**，高於全部敵人的持續 steering 上限：焰奴 2.5、影刺客 5.0、甲衛 1.8、Boss 2.1 units/s。只有已預兆的 lane dash／charge 可短暫更快。影刺客後撤目標縮到 2.1／2.65 units，後撤徑向速度最多使用自身上限的 72%，避免永久 kite。
- 每次普攻命中在 core 產生 deterministic enemy recoil 與短 recovery：第一／二／三段 recoil 0.08／0.11／0.32 units，reaction recovery 0.03／0.04／0.09s；位置必須 clamp，且不新增會取代敵人 attack state 的長硬直。render 以 light／heavy tier 顯示接觸爆閃、白閃壓縮後仰、方向碎屑；重擊 3 幀 visual hit-stop、2px shake，輕擊 2 幀、1px。core tick 與輸入不中止。
- core 公開 `ARENA_BOUNDS`、`clampToArena()`、`isInsideArena()` 作唯一真相來源。bounds 為 x = −11.2..11.2、y = −5.5..5.0 core units，映射到 640×360 canvas 的可走區；保留完整角色 sprite 邊距，HUD overlay 不參與世界邊界。每 tick 最終 player position、dodge endpoint、普攻／Q 推進、殘影瞬移、敵人 steering／knockback／dash／summon 都必須 clamp。
- 普攻判定與畫面扇形仍共同讀取 core 的 `ATTACK_RANGES_UNITS`／`ATTACK_HALF_ANGLES_RAD`。第一段骨白短弧、第二段餘燼橘反向弧、第三段火芯金長寬終結弧；弧寬、劍軌與 impact tier 不得只靠顏色區分。

真人第二次 Gate 3 回饋指出：敵人接近後原地停住、預兆畫面與實際範圍不一致、戰鬥節奏過慢。這是核心戰鬥退回，不是單純美術補強；因此本節明確覆蓋下方仍寫著「不授權修改 `src/core/`」的 2026-07-31 舊邊界。生命、傷害、護甲與敵人編成仍不變；只修正即時工程時序、移動 AI、攻擊幾何與表現同步。

- 上一輪的三段同值 0.08／0.05／0.15s 已由本輪「輕、輕、重」分級覆蓋；攻擊仍在各段 active window 開始時結算。
- 敵人不再以 1.2 units 為永久停車線。焰奴持續壓近並微幅追蹤；影刺客依攻擊次數換側、拉距後沿鎖定 lane 突進；甲衛維持中距並緩慢側向封位；Boss 依 smash／charge／summon 分別壓近、拉開與繞行。所有敵人套用以 id 決定方向的 deterministic separation，禁止 `Math.random()`。
- 預兆開始當 tick 將方向、起點、落點與範圍鎖入 `EnemyState.telegraphGeometry`。焰奴與甲衛使用不同半徑／半角的 cone；影刺客與 Boss charge 使用 lane；Boss smash 使用 circle；summon 使用固定 circles。core 命中與 render 提示只使用同一份公開 geometry helpers／constants；玩家離開鎖定提示即安全，留在提示內才命中。
- 敵人的實際 `velocity` 與 `locomotion` 進入公開狀態，render 依此顯示走路、側移、後撤、突進殘影、腳步塵與短 recovery。命中使用 40–60ms 純視覺 hit-stop 與 1–2px 短震動；core 100Hz 決定性 tick 不凍結。
- 首次攻擊延遲在接近期間同步倒數，避免敵人抵達後才重新空等；既有 `attack_interval_cycles`、HP、damage 與 content 數值不變。Gate 2 聚合 sim 因未修改 content 數值，仍以 1.1s cycle 模型重跑作回歸保護；它不模擬即時空間走位，不能代替本節新增的 core trajectory／geometry 測試。

## Gate 3 重製覆蓋（2026-07-31）

真人 Gate 3 已否決本文件原先的「單畫面黑曜決鬥場」以及後續採用的「160×90 巨像素黑底微縮舞台」呈現方向。Vertical Slice 的最新場景、角色、敵人、探索動線、動畫、特效、HUD、鏡頭與座標映射規格，以 [rework-0.1.0.md](./rework-0.1.0.md) 為準；本文件中與其衝突的 render／visual 描述、單畫面競技場假設與零資產限制均被覆蓋，不得再作為實作基底。

本文件的核心戰鬥規則、輸入與重綁要求、音訊事件意圖、敵人與印記內容、兩場 Vertical Slice 遭遇編成及所有既有平衡數值仍保留。重製只改變產品呈現與短地城流程，不授權修改 `src/core/` 平衡、`content/` 數值或 `sim/` 結果。

Scope：medium（提案 `scope_estimate`）；單局目標時間：**15–20 分鐘**

## 一句話

在單畫面的黑曜決鬥場中，玩家以**手動三段可打斷連擊**主動創造輸出窗口，穿越三個戰區擊敗敵群與終局 Boss；十二枚餘燼印記每一枚都直接改寫普攻、閃避、Q 或 E 的動作幾何，其中三條流派各有一枚印記同時重寫閃避與一項主動技能。

## 核心循環（三句話）

玩家用 WASD 走位、滑鼠左鍵打出三段連擊、空白鍵閃避取消後搖，在近戰交鋒中找出安全窗口清理場上敵人。每清理一場遭遇戰，就從三枚餘燼印記中選一枚，該印記會立刻改寫普攻、閃避、Q 或 E 其中之一的行為與場上可見表現，而不是單純加數值。三個戰區、六場遭遇戰、一次三選一之後，玩家帶著約六枚印記拼成的個人連段與走位風格，在決鬥場核心迎戰最終 Boss。

## 裂焰重新設計：與 Windblown／Pathogenic 的具體行為差異

競品查核指出「閃避留下可引爆火徑」已被 Windblown（Corrosive Wake）與 Pathogenic（Pyroflagellum）做過幾乎相同的機制——兩者都是「閃避／衝刺這個動作本身自動產生一段拖尾，任何經過拖尾的敵人都會受傷」，傷害來源與觸發者是同一個動作。

裂焰的 keystone 印記**餘燼核心**改為相反的因果方向：

1. **傷害物件由攻擊動作放置，而非閃避動作生成**：Q 不再是位移突進斬，而是在角色前方固定座標放置一枚「餘燼核」。
2. **核心武裝前後兩秒完全不具攻擊性**：`arm_delay_s = 2.0`，武裝前是暗紅色的純視覺標記；已武裝的核心也**不會**因敵人經過而自動觸發傷害——這是與兩款競品最核心的差異：牠們的拖尾是「經過即燒傷」的區域效果，餘燼核不是。
3. **閃避的路徑形狀因核心而改變**：當範圍內存在武裝核心時，閃避的位移軌跡從固定直線變為朝最近武裝核心微幅彎曲的弧線；掃過才會引爆，造成 18 點範圍傷害並給予 1.5 秒的普攻加成。沒有武裝核心在範圍內時，閃避恢復原本直線位移。
4. **普攻的第三段（裂焰連擊印記）刻意不引爆核心**：引爆規則只有「閃避掃過」單一入口，避免與 E（餘燼獻祭：一鍵引爆全場但冷卻拉長、不給加成）兩條路徑互相打架。

因果方向對照：

| | 觸發者 | 傷害物件生成者 | 對經過者是否自動傷害 | 位移路徑是否改變 |
|---|---|---|---|---|
| Windblown（Corrosive Wake） | 衝刺 | 衝刺本身 | 是 | 否，拖尾只是視覺殘留 |
| Pathogenic（Pyroflagellum） | 閃避 | 閃避本身 | 是 | 否 |
| 本作（餘燼核心） | 閃避 | 前一次 Q（攻擊動作） | 否，需玩家主動閃避掃過才引爆 | **是**，閃避路徑因核心存在而彎曲 |

`content/marks.json` 的 `ember-core` 條目 `differentiation_note` 欄位收錄完整文字，供美術／文案在 Vertical Slice 階段核對，避免行銷素材無意間走回「閃避拖尾」的既定印象。

## 控制與自訂鍵位規格

| 動作 | 預設 | 備註 |
|---|---|---|
| 移動 | WASD | 方向鍵固定作第二套備援，不可被重綁移除 |
| 攻擊 | 滑鼠左鍵 | 三段連擊 |
| 閃避 | 空白鍵 | 可取消普攻後搖 |
| 戰技一 | Q | |
| 戰技二 | E | |

規格細節（對應 `content/bindings.json`）：

- 所有動作判定一律使用 `KeyboardEvent.code`，**禁止 `event.key`**。滑鼠動作使用 `pointer_codes`（`Mouse0`–`Mouse4`，對應主／右／中／側鍵）。
- 玩家可在「設定 → 操作」重綁除方向鍵備援外的全部動作，包含移動的主鍵位（WASD 部分）與全部戰鬥動作，可綁一般鍵盤鍵或滑鼠主／右／中／側鍵。
- `non_bindable_codes` 固定排除 `Escape`、`Tab`、`F5`、所有 `Control/Alt/Shift/Meta` 修飾鍵與 `OSLeft/OSRight`，防止重綁破壞系統快捷鍵。
- 衝突處理：偵測到同一實體鍵已被其他動作占用時，UI 必須顯示該鍵原本的用途，並提供「交換」「覆蓋」「取消」三個選項；**不得靜默改寫**（`conflict_policy.silent_rebind_allowed = false`）。
- 對焦與清空：iframe 首次點擊後才接收遊戲輸入；`document.hidden`、視窗失焦（iframe blur）、`pointercancel` 事件觸發時，立即清空所有按住狀態（`focus_and_storage.clear_held_state_on`），避免切分頁回來後角色卡在「持續移動」或「持續蓄力」。
- 儲存：重綁資料一律透過 `@rogue-paradise/platform-sdk` 的版本化設定介面保存與讀取；**禁止 `localStorage`／`sessionStorage`／`indexedDB`**。資料缺失或版本不符時回退預設鍵位（`invalid_or_missing_falls_back_to: "default_codes"`）。
- 單一資料來源：HUD 提示、教學文字、設定頁全部讀取同一份 `content/bindings.json`／執行期 bindings 狀態；**任何提示文字都不得寫死「按 Q」「按空白鍵」等固定字串**，一律以目前實際綁定的鍵位動態渲染。

### 品味準則張力：WASD 與「不得依賴可被輸入法攔截的字元」

`studio/taste/principles.md` 的「網頁遊戲主要操作不得依賴可被輸入法攔截的字元」一條，其檢查方式寫的是「主要操作使用方向鍵與空白鍵」；本案預設主鍵位是 WASD，字面上像是牴觸。

**判斷**：這條準則的根因不是「WASD 這四個字母本身有問題」，而是 counter-overdrive 當時用 `event.key` 判定，導致中文輸入法組字（`compositionstart` 到 `compositionend` 之間）攔截了按鍵事件、角色收不到輸入。只要判定完全改用 `KeyboardEvent.code`——`code` 回報的是實體鍵位置，不受輸入法組字影響——WASD 在技術上與方向鍵一樣安全。本規格因此維持使用者明確指定的 WASD 為預設主鍵位，但：

1. 判定一律用 `code`（`KeyW`/`KeyA`/`KeyS`/`KeyD`），不使用 `key`。
2. 方向鍵固定作為第二套備援，永遠可用，滿足準則「方向鍵可用」的字面要求。
3. 全部戰鬥鍵位可重綁，介意 WASD 被輸入法影響的玩家（若使用某些非標準輸入法設定）可自行換成方向鍵或其他鍵。

**自動測試計畫**（Gate 3 前於 Vertical Slice 建立，於瀏覽器環境執行，非本原型模擬範圍）：

1. 對輸入處理模組觸發 `compositionstart`（模擬中文輸入法開始組字），期間持續派發 `KeyboardEvent('keydown', { code: 'KeyW' })`、`KeyA`、`KeyS`、`KeyD`、`Space`、`KeyQ`、`KeyE`，斷言角色的移動／攻擊／閃避／戰技狀態機正確接收到這些輸入且無延遲或遺漏。
2. 觸發 `compositionend` 後，再次派發同一組按鍵，確認組字結束後行為與組字前一致（不會殘留輸入法內部字元狀態影響判定）。
3. 反例測試：若處理模組誤用 `event.key`，上述測試應該失敗（`key` 在組字期間可能回傳輸入法候選字元而非字母），以此保證測試本身有偵測力，不是恆真斷言。
4. 游標位於任何 `<input>`／`<textarea>` 焦點時（例如重綁鍵位的輸入框本身），派發同一組按鍵，斷言遊戲邏輯**不**接收這些輸入（避免重綁畫面打字時意外觸發移動）。

## 玩家角色

- 生命：**220**（見〈平衡目標區間〉的數值出處說明——由 100 起算，因應敵人／Boss 血量為撐滿 15–20 分鐘目標而按比例調高後同步調高，維持相同的「每場戰鬥可承受多少次失誤」比例）。
- 移動速度：8 方向持續輸入，WASD 與方向鍵行為相同。
- 三段連擊：
  | 段 | 傷害 | 說明 |
  |---|---:|---|

印記選取規則（見 `sim/prototype.ts` 的 `eligibleMarks`）：

- Q 與 E 各自最多只有一枚印記能「完全重寫」（`slot: 'q' | 'e'`），一輪只會有一個 Q 版本與一個 E 版本生效，避免兩枚印記同時宣稱改寫同一顆按鍵。
- 標記 `requires` 的印記（雙核共振、餘燼獻祭、暗影收割、餘波護盾、鏡甲反傷、鐵壁連動）只有在其所需的 keystone 已被選取後才會出現在抽取池中，避免抽到「沒有系統可以掛載」的空氣印記。
- 閃避本身可以疊加多個流派的幾何修改（彎曲軌跡、精準殘影、格擋尾段）——這三者互相獨立生效、不衝突，因為它們各自綁定不同的觸發條件（核心存在／精準時機／每次成功閃避後的機率格擋尾段）。

## 三條流派的成形路徑與差異表

| 流派 | 成形路徑 | 核心矛盾／取捨 |
|---|---|---|
| 裂焰 | 先選餘燼核心建立引爆系統，再依需求補雙核共振（拉長連鎖）或餘燼獻祭（穩定但無加成） | 「精準走位換取閃避引爆的攻擊加成」vs「一鍵引爆但冷卻更長」 |
| 影步 | 先選精準殘影建立殘影／E 資源，再補突進追擊（反擊輸出）或虛影重置（閃避頻率）或暗影收割（Q 範圍點殺） | 「E 瞬移單體高傷」vs「Q 範圍不消耗殘影」 |
| 守勢 | 先選蓄能反震建立層數系統，再補餘波護盾（格擋保底）、鏡甲反傷（低風險反傷）或鐵壁連動（近身群戰） | 「蓄滿層數才能兌現高額 E 傷害」vs「持續小額反傷與範圍優勢」 |

三條流派在 `sim/prototype.ts` 的 `markTriggers`／`decisionSignature` 上會產生彼此不同的觸發分佈（例如裂焰跑會累積 `ember-core`／`twin-core-resonance` 觸發次數，守勢跑會累積 `charged-retaliation`／`aftershock-shield`），10,000 局模擬下三流派的 `buildSignature` 各自形成獨立、不重疊的印記組合集合（見〈平衡目標區間〉）。

## 平衡目標區間

|---|---|---|---|

| 單局時長 | 15–20 分鐘 | 中位數 **15.58 分鐘**（p10 14.93 分鐘／p90 16.31 分鐘） | 對應提案「15–20 分鐘」；MVP 僅 3 戰區、7 場戰鬥，時長預算由教學／換場走位／印記選擇畫面等非戰鬥節奏（合計約 6–7 分鐘固定開銷）與戰鬥本身共同組成，模擬只計算離散化的「連擊循環」與固定節奏開銷，不含真人操作的個體差異。 |

### 2026-07-30 Gate 2 修訂：雙核共振修好、餘波護盾還原設計並登記已知限制、鐵壁連動修正實作缺陷

Balance Engineer 的可行性報告（`sim/reports/2026-07-30-gate-2-feasibility.md`）診斷出雙核共振（0.63 次／局）與餘波護盾（1.08 次／局）觸發率過低，兩者根因不同、處置也不同：

- **雙核共振（已修好）**：前置條件「兩枚核心同時武裝」本身太窄（Q 冷卻 5 秒＋武裝延遲 2 秒疊加，第一核幾乎總在第二核武裝前就被引爆），是內容數值層級的設計問題。修訂：`chain_probability_pct` 由 40 提高到 100（Balance 已驗證單獨調整安全但不夠），並新增雙核共振專屬的縮短 Q 冷卻（`q_cooldown_s: 2`，覆蓋餘燼核心的 5 秒），讓兩核的武裝時間差從 5 秒壓縮到 2 秒。修好後觸發率回升至 15.3 次／局，`gate2.markTriggerHealth` 對此印記無異議。

- **餘波護盾（還原設計＋登記已知限制，不重新設計）**：Balance 的原始診斷是「舊設計要求蓄能滿 3 層，與蓄能反震自己的 E（層數 >0 即自動施放並清空）互相搶奪同一份『層數』資源」，並據此建議把觸發條件改為「E 施放後機率觸發格擋」。Designer 依此建議一度重新設計並實測（機率 25%×減傷 50% 的組合能讓觸發率達標且不擊穿其餘門檻），但 **Studio Head 審閱後駁回這個重新設計**，理由：(1) 新設計的實際觸發條件與效果都與閃避無關，讓 `changes_actions: ['dodge']` 變成假 metadata；(2) 新設計是機率×減傷、沒有任何形狀／位置／操作決策改變的純數值印記，牴觸 spec 的招牌主張「沒有一枚是純數值印記」與 Designer AGENT.md 的完成判準；(3) 兩個折扣數字是為了同時滿足「觸發率 ≥3」與「不擊穿勝率門檻」反推校準出來的指標驅動結果，不是設計驅動。

  Studio Head 判定：餘波護盾低觸發率的**根因是本原型的自動施放 AI 缺乏「屏住層數」這個策略選項**（模型限制）——AI 只要層數 >0、冷卻好就會自動施放 E 並清空層數，無法模擬真人玩家「屏住 3 層換格擋保底」vs「立即花掉層數換傷害」的策略性取捨；這個取捨本身是設計的特色，不是缺陷。Balance 測過的「讓 E 等到滿層才發」觸發率降到 0.74，只證明另一套同樣僵硬的自動規則也不行，不能證明真人做不到。因此餘波護盾**還原為原始設計**（`required_stacks: 3`、滿層必定完全格擋、`one_time_next_e_bonus_pct: 20`），觸發率回到 1.08 次／局（低於健康門檻，見上表），並在 `sim/report.ts` 的 `markHealth.knownPrototypeAiLimitations` 與 `sim/prototype.test.ts` 的 `KNOWN_STRUCTURALLY_NARROW_MARKS`（白名單長度鎖死為 1）明確登記為「原型 AI 無法模擬人類的層數保留策略，實際效用待 Gate 3 真人試玩量測」。**`gate2.markTriggerHealth` 因此如實為 `false`**——這是正確且可接受的結果，誠實反映「有一枚印記的效用待 Gate 3 驗證」，不得為了讓它變綠而放寬判準或改設計。

- **鐵壁連動（修正實作缺陷）**：`sim/prototype.ts` 原本把 `combo_no_reset_chance_pct` 實作成「15% 機率造成 +8 額外傷害」，與 `content/marks.json`／本規格描述的「15% 機率連段不重置」（操作節奏不中斷）矛盾——是內容正本與程式碼互相衝突的實作缺陷，任務 A 的重構過程中發現但當時未修正，本輪已修正：15% 機率時，這次攻擊的連擊效率固定取滾動範圍上限（視為接住完整連段），而非額外加一筆固定傷害。同 seed 30,000 局重測：修正前後 `bulwark-chain` 每局觸發次數 11.97→11.59（仍健康），對 `winRate`／`schoolWinRateSpread`／`topFiveBuildShare` 等 Gate 2 指標影響在 0.1pp 以內，不影響任何判定。

### 模擬近似落差揭露：蓄能反震的格擋尾段機率、精準殘影的殘影到期未建模

任務 A 的重構要求「所有平衡相關數值都從 content/*.json 讀取」，但兩個地方目前仍有模擬近似值無法忠實反映內容欄位，明確揭露如下，避免靜默存在：

- **蓄能反震的 `dodge_trailing_parry_s: 0.15`**：字面秒數換算（除以連擊循環時間 1.1 秒）應為 13.6%，但敏感度測試顯示這個量級對本模型的「每次判定各自獨立擲骰」機制過強——單獨把它從 0 調到 13.6% 就讓守勢勝率跳 +14 個百分點。模擬因此改用校準過的保守值 **3%**，讓格擋尾段「存在且可被 `blockedHits` 觀測到」但不成為守勢的主要防禦來源。這個 13.6% vs 3% 的落差本身就是任務 A 想消除的那類問題（欄位無法忠實驅動模擬），只是這裡沒有更好的解法：問題根源是模型把「連續時間窗口」離散化成「單次判定機率」時必然損失資訊。**Gate 3 待驗**：真人測試蓄能反震的格擋尾段手感後，重新校準這個近似值。
- **精準殘影的 `afterimage_duration_s: 1.6`**：設計描述殘影應在 1.6 秒後自動到期消失，但 `sim/prototype.ts` 目前完全沒有讀取或建模這個欄位——`shadowStacks` 只靠 E／Q 消耗，不會因時間經過而過期，可能高估了影步玩家能囤積的殘影層數與 E 的可用頻率。本輪未建模，因為需要追蹤「每個殘影各自的存續時間」，是比較大的模型改動；已在 `sim/prototype.ts` 加註解明確標記此欄位未被讀取。**Gate 3 待驗**：真人測試影步的殘影／E 循環節奏是否符合「1.6 秒到期」的設計意圖，若模擬因此高估了影步的實際強度，需回頭建模或調整。

### 誠實揭露：Build 集中度是本規格最不確定的一項

Balance 模擬顯示 `topFiveBuildShare` 為 53.6%（本規格 10,000 局重現指令，隨 Gate 2 修訂略有波動），雖在收緊後的 ≤58% 門檻內，但明顯高於一般理想值（例如 counter-overdrive 的 ≤45%）。根本原因是本案刻意收斂成「12 枚印記、每輪僅選 6 枚、且多數印記需要 keystone 前置」的小池子（這是競品查核要求的「不得長成技能樹」的直接後果），加上原型的抽取 AI 會偏好玩家的流派親和力——這使得同流派的跑局最終選到的印記組合天然相似。這不是明顯的「支配性策略」（三流派勝率幾乎打平），而是內容池規模本身的結構性限制。建議 Balance Engineer 在 Gate 2 之後檢視是否要：（a）接受這個集中度、（b）調整抽取權重讓玩家更容易拿到跨流派印記、或（c）視 Gate 3 實際玩家選擇（而非本原型簡化 AI）重新量測，因為真人會依戰況做情境判斷，多樣性可能高於本模擬。

## Gate 3 待驗清單（無頭模擬驗不到的手感項目）

- 閃避無敵幀窗口（設計目標 0.28 秒）與敵人預兆時間（350/500/800ms）搭配後的實際手感是否符合「看得到、來得及、但不能無腦連按」。
- 閃避路徑因餘燼核心彎曲、蓄能反震尾段格擋判定，實機測試是否清楚可辨（不只是模擬中的機率參數）。
- 三種敵人／Boss 預兆的實際可讀性：光暈收縮、殘影軌跡、地面扇形範圍在真實畫面更新率下是否足夠清楚，不看文字也能分辨。
- 印記觸發特效（核心弧線、殘影、護環）在多個印記同時生效時是否互相干擾視覺可讀性。
- 〈品味準則張力〉章節的中文輸入法自動測試在真實瀏覽器（含常見中文輸入法）下的實測結果。
- iframe 失焦／分頁隱藏／pointer cancel 的清空按住狀態，實機測試各種切換時機。
- Boss 三階段轉換的戲劇性演出節奏，是否讓玩家明確感知到「狂暴階段開始了」而不只是數值變化。
- 三選一印記選擇畫面的資訊呈現是否讓玩家不讀長句也能判斷取捨（對應「詞條必須直接演示」準則）。
- 單局實際遊玩時長對照模擬的 15–20 分鐘目標（模擬僅以固定秒數近似教學／換場／選擇節奏，真人操作節奏會有個體差異）。
- Build 集中度（見〈誠實揭露〉）在真人玩家的實際選擇下是否比原型簡化 AI 的模擬結果更分散。
- **最高優先（Studio Head 2026-07-30 指定）**：量測真人玩家選取餘波護盾後，實際「屏住蓄能層數不立即施放 E」的頻率與持續時間。本原型的自動施放 AI 一律層數 >0 就自動花掉，無法驗證這枚印記真正的效用；若真人玩家也幾乎不會主動屏住層數（例如戰鬥節奏太快、沒有餘裕做這個決策），才需要回頭重新設計此印記，而不是現在就依模擬結果動手。
- 蓄能反震閃避尾段格擋判定的真人手感校準：模擬用 3% 近似字面 13.6% 的换算（見〈模擬近似落差揭露〉），需要真人測試判斷這個近似是否合理、是否需要調整格擋尾段本身的秒數或觸發機率。
- 精準殘影的殘影／E 循環節奏真人測試：確認模擬未建模 `afterimage_duration_s`（1.6 秒到期）是否讓影步的實際強度被高估。
